# DevLog Database Performance & Architecture Analysis

This document provides empirical performance benchmarks, query execution plans (`EXPLAIN ANALYZE`), index efficiency analysis, and architectural database design decisions for the DevLog application.

## 1. Benchmarking Dataset Setup

All performance measurements in this document were captured on PostgreSQL with **20,000 synthetic incidents** generated by `backend/prisma/seed-bulk.js` using the dedicated npm script:

```bash
npm run seed:bulk
```

- **Total Incidents**: 20,000
- **Status Distribution**:
  - `OPEN`: 1,012 (~5.1%)
  - `RESOLVED`: 18,988 (~94.9%)
- **Post-Mortem Records**: 18,988 (1:1 relation for every resolved incident)
- **Time Range**: Distributed randomly across the preceding 365 days
- **Services**: Distributed across all active services (`User Auth`, `Billing Engine`, `Notification API`, etc.)

To return the database to the clean 3-service, 3-incident baseline at any time:
```bash
npm run seed:reset
```

## 2. EXPLAIN ANALYZE Evidence

### Query A: Open Incidents, Newest First, Page 1

The primary query powering the Incident Dashboard (`status = OPEN`, sorted newest first, first page of 10 items):

```sql
SELECT id, title, description, severity, status, "createdAt", "serviceId"
FROM "Incident"
WHERE status = 'OPEN'
ORDER BY "createdAt" DESC
LIMIT 10 OFFSET 0;
```

#### Plan 1: WITHOUT Indexes (Sequential Table Scan + Sort)

```text
Limit  (cost=799.05..799.07 rows=10 width=175) (actual time=1.489..1.491 rows=10.00 loops=1)
  Buffers: shared hit=527
  ->  Sort  (cost=799.05..801.58 rows=1015 width=175) (actual time=1.488..1.489 rows=10.00 loops=1)
        Sort Key: "createdAt" DESC
        Sort Method: top-N heapsort  Memory: 28kB
        Buffers: shared hit=527
        ->  Seq Scan on "Incident"  (cost=0.00..777.11 rows=1015 width=175) (actual time=0.010..1.382 rows=1015.00 loops=1)
              Filter: (status = 'OPEN'::"Status")
              Rows Removed by Filter: 18994
              Buffers: shared hit=527
Planning Time: 0.178 ms
Execution Time: 1.513 ms
```

#### Plan 2: WITH Partial Index (`Incident_open_createdAt_idx`)

```text
Limit  (cost=0.28..21.03 rows=10 width=175) (actual time=0.027..0.034 rows=10.00 loops=1)
  Buffers: shared hit=8 read=2
  ->  Index Scan using "Incident_open_createdAt_idx" on "Incident"  (cost=0.28..2107.36 rows=1015 width=175) (actual time=0.026..0.032 rows=10.00 loops=1)
        Index Searches: 1
        Buffers: shared hit=8 read=2
Planning Time: 0.215 ms
Execution Time: 0.043 ms
```

#### Plain Language Explanation:
1. **Sequential Scan vs. Index Scan**:
   - In **Plan 1 (No Index)**, PostgreSQL must read every single data page on disk (all **527 shared buffers**). It inspects all 20,000 rows one by one, discards 18,994 resolved rows (`Rows Removed by Filter: 18994`), collects the 1,015 matching rows in RAM, and performs an in-memory **Top-N heapsort** to find the 10 newest rows.
   - In **Plan 2 (Partial Index)**, the database navigates directly into the pre-sorted B-Tree index structure. Because the index already contains only open incidents pre-ordered by `"createdAt" DESC`, PostgreSQL reads only the first 10 index entries (**10 buffers** total) and immediately halts.
2. **Estimated vs. Actual Rows**:
   - PostgreSQL estimated 10 rows for the `LIMIT` and 1,015 total matching rows (`rows=1015`). The actual rows returned were exactly 10.00. The query planner's selectivity statistics (`ANALYZE`) were accurate within 0.3%.
3. **Execution Time**:
   - Without the index: **1.513 ms**.
   - With the partial index: **0.043 ms**.
   - **Performance Gain**: **35.1x faster** execution with a 98% reduction in buffer I/O.

### Index Storage Footprint: Full vs. Partial Index

We inspected PostgreSQL catalog tables (`pg_indexes` and `pg_relation_size`) to measure on-disk index sizes with 20,000 records:

| Index Name | Type | Size | Explanation |
| :--- | :--- | :--- | :--- |
| `Incident_pkey` | Primary Key (B-Tree) | **456 kB** | Indexes all 20,000 incident IDs. |
| `Incident_status_createdAt_idx` | Compound Index | **632 kB** | Indexes `(status, createdAt)` across all 20,000 rows. |
| `Incident_open_createdAt_idx` | **Partial Index** | **40 kB** | **Only indexes rows where `status = 'OPEN'` (~1,000 rows).** |
| `Incident_serviceId_idx` | Foreign Key Index | **160 kB** | Indexes `serviceId` for joins. |

#### Why the Partial Index is Superior:
- **15.8x Smaller in RAM and Disk**: Because open incidents represent only ~5% of all incidents, indexing only open rows requires **40 kB** compared to **632 kB** for the full index.
- **Cache Locality**: A 40 kB index fits entirely inside the CPU L1/L2 cache, avoiding buffer cache churn.
- **Zero Write Overhead on Resolutions**: When an incident transitions from `OPEN` to `RESOLVED`, it is automatically deleted from the partial index, leaving the index compact and clean.

### Query B: All Incidents for One Service

```sql
SELECT id, title, description, severity, status, "createdAt", "serviceId"
FROM "Incident"
WHERE "serviceId" = 31;
```

#### Plan 1: WITHOUT Index (`Incident_serviceId_idx` dropped)

```text
Seq Scan on "Incident"  (cost=0.00..777.11 rows=2471 width=175) (actual time=0.011..1.532 rows=2471.00 loops=1)
  Filter: ("serviceId" = 31)
  Rows Removed by Filter: 17538
  Buffers: shared hit=527
Planning Time: 0.203 ms
Execution Time: 1.601 ms
```

#### Plan 2: WITH Index (`Incident_serviceId_idx`)

```text
Bitmap Heap Scan on "Incident"  (cost=31.44..589.33 rows=2471 width=175) (actual time=0.192..0.714 rows=2471.00 loops=1)
  Recheck Cond: ("serviceId" = 31)
  Heap Blocks: exact=523
  Buffers: shared hit=523 read=4
  ->  Bitmap Index Scan on "Incident_serviceId_idx"  (cost=0.00..30.82 rows=2471 width=0) (actual time=0.139..0.139 rows=2471.00 loops=1)
        Index Cond: ("serviceId" = 31)
        Index Searches: 1
        Buffers: shared read=4
Planning Time: 0.398 ms
Execution Time: 0.793 ms
```

#### Plain Language Explanation:
- Without the index, PostgreSQL performs a full table scan over 20,000 records and discards 17,538 non-matching rows.
- With `Incident_serviceId_idx`, PostgreSQL scans the compact index first (`Bitmap Index Scan`, requiring only **4 buffer reads**), builds a bitmap of matching pages, and only visits the necessary heap pages.
- **Execution Time drops from 1.601 ms to 0.793 ms (50% reduction)**.

## 3. Analytics Endpoint: CTE and Window Function

The endpoint `GET /api/v1/stats/services` uses `prisma.$queryRaw` with a tagged template string (`Prisma.sql` semantics) to compute service rankings and duration metrics:

### SQL Implementation ([backend/src/repositories/stats.repository.js](file:///c:/dev/Devlog/backend/src/repositories/stats.repository.js#L42-L80))

```sql
WITH service_metrics AS (
  SELECT
    s.id,
    s.name,
    s.environment,
    CAST(COUNT(i.id) AS INTEGER) AS "incidentCount",
    CAST(COUNT(CASE WHEN i.status = 'RESOLVED' THEN 1 END) AS INTEGER) AS "resolvedCount",
    CAST(COALESCE(SUM(pm."timeSpentMinutes"), 0) AS INTEGER) AS "totalMinutesSpent",
    ROUND(
      COALESCE(
        AVG(CASE WHEN i.status = 'RESOLVED' THEN pm."timeSpentMinutes" END),
        0
      )::NUMERIC,
      1
    )::FLOAT AS "avgMinutesPerResolved"
  FROM "Service" s
  LEFT JOIN "Incident" i ON s.id = i."serviceId"
  LEFT JOIN "PostMortem" pm ON i.id = pm."incidentId"
  GROUP BY s.id, s.name, s.environment
)
SELECT
  id,
  name,
  environment,
  "incidentCount",
  "resolvedCount",
  "totalMinutesSpent",
  "avgMinutesPerResolved",
  RANK() OVER (ORDER BY "totalMinutesSpent" DESC)::INTEGER AS rank
FROM service_metrics
ORDER BY rank ASC, name ASC;
```

### Key Technical Details:
1. **Common Table Expression (CTE)**:
   - The `WITH service_metrics AS (...)` clause creates a clean modular query pipeline that aggregates joins between `Service`, `Incident`, and `PostMortem` before ranking.
2. **Window Function (`RANK() OVER`)**:
   - `RANK() OVER (ORDER BY "totalMinutesSpent" DESC)` computes the ordinal rank of each service directly in the database engine across the result set partition. If two services tie on total minutes spent, they receive the same rank.
3. **BigInt Serialization Protection**:
   - PostgreSQL aggregate functions (`COUNT`) return 64-bit BigInts by default. Node.js `JSON.stringify()` throws a fatal `TypeError: Do not know how to serialize a BigInt` when attempting to serialize JavaScript `BigInt` values.
   - We explicitly cast all counts and window calculations to `INTEGER` (`CAST(COUNT(...) AS INTEGER)` and `::INTEGER`) and averages to `FLOAT`. This ensures seamless JSON API serialization without external polyfills.

## 4. Advanced Database Architecture & Concurrency

### A. The N+1 Query Problem & How DevLog Avoids It

#### The Problem:
When querying a list of 10 incidents to display on the dashboard, a naive implementation fetches the 10 incidents in one query, then inside a `forEach` loop executes an additional query for each incident's service:
- 1 initial query + 10 subsequent queries = **11 queries (N+1)**. For 50 rows, this means 51 separate database roundtrips.

#### How DevLog Solves It:
In [backend/src/repositories/incident.repository.js](file:///c:/dev/Devlog/backend/src/repositories/incident.repository.js#L14-L24), our repository query uses:

```javascript
prisma.incident.findMany({
  where,
  skip,
  take,
  orderBy: { createdAt: "desc" },
  include: {
    service: true,
  },
});
```

Under the hood, Prisma batches this into either an optimized SQL `JOIN` or exactly two database roundtrips regardless of page size:
```sql
SELECT * FROM "Incident" WHERE status = 'OPEN' ORDER BY "createdAt" DESC LIMIT 10;
SELECT * FROM "Service" WHERE id IN (31, 32, 33);
```
Total queries: **2 (O(1) constant time)**, completely eliminating the N+1 problem.

### B. Transaction Safety, MVCC, and Race-Condition Protection

#### PostgreSQL Default Isolation Level: Read Committed
By default, PostgreSQL operates under the **Read Committed** isolation level. Under Read Committed:
- A query only sees rows committed before the query began.
- It never sees dirty (uncommitted) writes.
- Multiple transactions can run simultaneously without blocking reads.

#### How MVCC (Multi-Version Concurrency Control) Works:
PostgreSQL implements MVCC by attaching hidden system columns to every row:
- `xmin`: The transaction ID that inserted the row.
- `xmax`: The transaction ID that updated or deleted the row.
When a row is updated, PostgreSQL does not overwrite the row in place; instead, it marks the existing tuple's `xmax` and writes a new tuple version with the new data. Readers continue reading older valid versions while writers write new versions without locking each other.

#### The Race Condition: Simultaneous Incident Resolution
Imagine two engineers, Alice and Bob, have the same open incident open on their screens and click "Resolve" at the exact same millisecond.

#### Why a Read-Then-Write Check Fails:
If the code did:
1. `SELECT status FROM Incident WHERE id = 1` -> both see `"OPEN"`.
2. `UPDATE Incident SET status = 'RESOLVED'` -> both succeed!
3. Result: Duplicate post-mortems or corrupted state.

#### The DevLog Solution ([backend/src/services/incident.service.js](file:///c:/dev/Devlog/backend/src/services/incident.service.js#L42-L75)):
DevLog uses an atomic condition check inside a single database transaction:

```javascript
const result = await prisma.$transaction(async (tx) => {
  const updated = await tx.incident.updateMany({
    where: {
      id: incidentId,
      status: "OPEN", // Atomic guard condition
    },
    data: {
      status: "RESOLVED",
    },
  });

  if (updated.count === 0) {
    // Row was either not found or already resolved by another transaction
    throw new AppError("Incident is already resolved.", 409, "CONFLICT");
  }

  return tx.postMortem.create({
    data: {
      incidentId,
      rootCause,
      resolutionSteps,
      timeSpentMinutes,
    },
  });
});
```

#### How PostgreSQL Handles This:
1. When Alice's transaction executes `updateMany`, PostgreSQL places an **exclusive row-level write lock** on the incident row.
2. Bob's transaction attempts to execute `updateMany` on the same row and is put into a sleep/wait queue until Alice's transaction completes.
3. Alice's transaction commits: status is now `RESOLVED`.
4. Bob's transaction wakes up. Under PostgreSQL's **Read Committed** rules, when a transaction wakes up after waiting on a row lock, it re-evaluates the `WHERE` clause against the newly committed version of the row.
5. In the new version, `status` is `'RESOLVED'`. The condition `status = 'OPEN'` evaluates to `FALSE`!
6. Bob's `updateMany` updates **0 rows** (`count: 0`).
7. DevLog immediately throws an `AppError(..., 409, "CONFLICT")` and aborts Bob's transaction, preventing any duplicate post-mortem.

### C. Connection Pooling & Shared PrismaClient

#### How Many Connections Prisma Opens by Default:
By default, the Prisma client formula for pool size is:
$$\text{pool\_size} = \text{num\_physical\_cpus} \times 2 + 1$$
On an 8-core CPU, this defaults to **17 connections**. The connection limit can also be explicitly controlled via the `connection_limit` parameter in `DATABASE_URL` (e.g. `?connection_limit=10`).

#### Why DevLog Uses One Shared PrismaClient Instance:
Every connection in PostgreSQL is a separate OS process that consumes:
- ~10 MB of RAM for connection overhead and memory buffers.
- File descriptors and socket handlers.
- Process context switching overhead.

If every service or repository instantiated its own `new PrismaClient()`:
- 10 route files $\times$ 17 connections = **170 connections**.
- PostgreSQL's default `max_connections` is **100**. The server would immediately crash with `FATAL: remaining connection slots are reserved for non-replication superuser connections`.

By creating a single shared `PrismaClient` in [backend/src/config/db.js](file:///c:/dev/Devlog/backend/src/config/db.js) and importing that single reference across all repositories, the entire application shares one bounded connection pool with automatic queueing, health checks, and connection reuse.
